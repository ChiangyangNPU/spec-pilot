# SpecPilot：规格驱动的四阶段自动开发流水线

你要按"需求 → 设计 → 编码 → 测试"四个阶段驱动一个项目从想法到可交付，执行者是你，决策节点是用户。核心原则：**每阶段产出文档、下一阶段以文档为唯一输入、测试对需求负责而不是对代码负责。**

## 流程总览

```
用户提需求 → [阶段1 需求] → 👤确认SRS → [阶段2 设计] → 任务拆解 → 冻结测试用例
          → 一致性检查 → [阶段3 编码] → [阶段4 测试] ──不通过──→ 缺陷回传修复（最多5轮）
                              │通过
                              ▼
                        收敛核对 → 汇总交付物 → 👤最终验收 → 归档与复盘
```

必须停下来等待用户**决策**的节点只有两个：**确认 SRS** 和 **最终验收**。除此之外的交互仅限阶段 1 的澄清提问（两轮以内）；设计、编码、测试全部自动完成，不要向用户请求中间审批，也不要为汇报进度而打断用户。

**通用规则**：每个阶段收尾时，对照该阶段的模板逐项自检产物完整性（该有的图、表、清单缺一不可），补齐后才进入下一阶段；产物落在文档里的决策与代码的行为必须一致。

## 流程分级（借鉴 BMAD 的 right-sizing：流程大小匹配变更规模）

| 级别 | 适用场景 | 产物与裁剪 |
|------|----------|------------|
| 轻量级 | 单点修改：影响范围在一个模块内、不新增接口/表结构、验收标准清晰 | 产物放 `docs/changes/<变更名>/`：`spec.md`（需求、验收标准与实现要点合并，模板见 [references/lite-spec-template.md](references/lite-spec-template.md)）+ `04-test-cases.md` + `06-test-report.md`。任务拆解省略，图表按需；已有 `00-constitution.md` 则遵守，没有不新建 |
| 完整级 | 新功能、新项目、跨模块改动 | 全流程，产物按文件契约放 `docs/`，不裁剪 |

级别在开工前判定，并用一句话向用户说明所选级别与理由（告知即可，不必等待答复）；拿不准时按完整级走。**裁剪的是文档，不是验证**——任何级别都必须冻结测试用例并真实执行测试。

**轻量级升级机制**：级别是开工前的预判，动手后发现实际越界并不罕见。轻量级执行中一旦发现改动超出裁剪边界（需要新增对外接口/表结构、影响范围扩散到其他模块、验收标准无法在原 spec.md 内讲清），立即暂停编码、用一句话告知用户后升级为完整级：已写的 `spec.md` 内容拆分并入 `docs/01-srs.md`、`02-design.md`、`03-tasks.md`，补齐设计覆盖与任务预估，冻结用例按完整级门禁重新核对后再继续——不带着"轻量级"的残缺文档硬走完整级的改动。

## 上下文隔离（完整级大项目）

"每阶段产出文档、下一阶段以文档为唯一输入"的设计天然支持上下文隔离。完整级运行在项目规模较大、或主代理上下文吃紧（阶段 0 摸底与长设计/编码对话堆积）时，**每个阶段交给一个独立、干净上下文的子代理执行**：子代理的输入只有该阶段的上游产物（SRS、设计文档、constitution 等对应文档），主代理只负责编排、两个检查点的交互和跨阶段产物核对，不参与具体执行。轻量级变更保持单会话。三点约束：

- 阶段 4 的用例生成本就有强制子代理规则（见"冻结测试用例"）；其余阶段采用子代理路线时，收尾产物由主代理对照模板核对通过才可进入下一阶段。
- 子代理产出的一切必须落在文档里——没写进 `docs/` 的信息不构成产物，也不得作为下一阶段输入（口口相传等于没传）。
- 角色分离收益叠加：设计子代理看不到需求澄清的对话噪音，编码子代理看不到设计摇摆的过程，各阶段只认契约。

## 阶段 0：启动

1. 在项目根目录创建 `docs/` 目录，所有阶段产出物放这里。
2. **读取复盘记录**：若存在 `docs/lessons.md`（之前运行留下的经验教训），先读再开工——它是流程自我改进的载体。
3. **项目约束（借鉴 Spec Kit 的 constitution）**：查找现有约束来源——AGENTS.md、CLAUDE.md、README 中的技术栈说明、.editorconfig、CI 配置等。**发现任一来源即摘录要点生成 `docs/00-constitution.md`，无需询问用户**（约束是从事实提炼的，不是新决策）；仅当完全没有现成来源时才请用户确认技术栈边界、规范要点与质量底线后创建。设计与编码阶段必须逐条遵守，约束变更先改此文件。
4. **改造既有工程时**，先摸清现状再动手：技术栈与版本、构建/测试命令、目录组织、代码风格、已有的测试框架。后续设计、编码都跟随现有约定，不按个人偏好另起炉灶。
5. 如果项目目录还不是 git 仓库，执行 `git init`。每个阶段完成、产物定稿后提交一次（提交信息注明阶段），保证任何时刻可回溯。**提交与推送动作遵循宿主工具的授权约定**：若宿主环境要求用户显式授权才允许提交，则只完成暂存并给出提交命令/信息，不擅自执行 commit，更不得自行 push。
6. 如果用户输入极其简短（如"做一个待办事项应用"），先进入阶段 1 的澄清对话，不要自己补全需求。
7. **中断恢复**：若 `docs/` 下已存在本流水线的产物（跨会话续跑、上下文超限后重开），既不要从头重跑、也不要凭记忆跳阶段。依据**已有产物文件 + `03-tasks.md` 的勾选状态**客观判定断点（最新定稿产物对应阶段的下一个动作即为续跑点），列出"已完成 / 进行中 / 未开始"清单向用户确认续跑点后继续；已冻结的 SRS 与用例不重新基线化，未跑完的阶段从断点处接着执行。轻量级变更以 `docs/changes/<变更名>/` 下产物同样判定。

## 阶段 1：需求分析（角色：需求分析师）

1. 阅读用户需求。信息不足时**一次性**提出澄清问题（目标用户、核心场景、不做什么、怎样算成功）。用户回答后如仍有关键缺口，最多再补一轮追问（合计不超过两轮），其余缺口按合理默认值处理并登记到 SRS 的"已按默认值处理的假设"表——流水线不能卡在反复提问上。
2. 按 [references/01-srs-template.md](references/01-srs-template.md) 生成 `docs/01-srs.md`。SRS 不只是需求清单，必须包含：参与者与用例图、核心用例描述表、端到端业务流程图——图表用 Mermaid 语法。
3. 关键规则：**每条功能需求必须附带可自动验证的验收标准**。"响应快"不行，"查询响应 ≤ 2 秒"才行——因为阶段 4 的测试用例将直接从验收标准翻译而来，这是整条流水线能自动闭环的前提。无法量化的，给出可操作的验证方式。
4. 缺失的信息标记为"待确认"，禁止编造。
5. **👤 人工检查点**：向用户展示 SRS 摘要（功能清单 + 验收标准 + **两轮澄清后按默认值处理的假设清单**——"我替你假设了什么"恰是用户最该过目并签字的内容），请求确认。用户确认前不得进入设计阶段。
   - 例外：用户已事先声明全自动模式（如"跳过确认""全自动跑"），则展示 SRS、显著标注"已跳过人工确认"后继续。

## 阶段 2：设计（角色：架构师）

1. 以 `docs/01-srs.md` 为唯一输入，生成 `docs/02-design.md`（模板见 [references/02-design-template.md](references/02-design-template.md)）：技术选型及理由、系统架构图、模块划分与依赖图、核心类图、关键流程时序图、数据库 E-R 图与表结构、接口定义、目标目录结构。全部图表用 Mermaid 语法，每个关键用例至少对应一张时序图。
2. 防过度设计：满足当前需求的前提下选择最简单的方案；用户没有指定技术栈时，选生态成熟、你确实掌握的，不追新。
3. 对照 SRS 逐条检查设计覆盖了全部功能需求，在文档末尾附覆盖对照表。

## 任务拆解（借鉴 Spec Kit 的 tasks：设计后、编码前）

以 `docs/02-design.md` 为依据生成 `docs/03-tasks.md`（模板见 [references/03-tasks-template.md](references/03-tasks-template.md)）：把实现拆成有序、可独立验证的任务。每个任务包含：编号、目标、涉及模块、完成判据、预估工时、依赖关系。

- **粒度标准**：一个任务一次提交、可独立验证；预计超过半天工作量或横跨多个模块的任务继续拆。
- 编码阶段按此清单顺序推进、逐项勾选；轻量级变更可省略本节。

## 冻结测试用例（设计后、编码前——流水线的生命线）

1. 在写任何代码之前，仅依据 `docs/01-srs.md` 和 `docs/02-design.md` 生成 `docs/04-test-cases.md`（模板见 [references/04-test-cases-template.md](references/04-test-cases-template.md)）：测试用例表（用例 ID、来源需求编号、前置条件、步骤、输入、预期结果、失效检测点）+ 需求覆盖矩阵。
2. 为什么必须在编码前：测试用例的价值在于验证"需求是否被正确实现"。如果看了实现再写用例，用例会不自觉复述实现的行为——AI 既写又测会"自我认同"，测试就形同虚设。编码前生成是单会话内实现角色分离最可靠的方式。
3. **冻结规则**：进入编码后不得因实现细节修改用例。执行中发现用例本身确实有错，允许修正，但必须在用例表中注明"变更记录：原因"。**接手已有代码的项目时，用例生成必须委托给一个子代理执行，子代理的输入只给 SRS 和设计文档，不给任何现有代码**——因为阶段 0 摸底和改造设计都会接触代码，主代理自己生成用例很难不受实现影响，子代理的干净上下文是角色分离的保证。
4. **一致性检查（借鉴 Spec Kit 的 analyze，编码前门禁）**：对照检查四份产物——SRS 每条需求是否被设计覆盖（设计文档的覆盖对照表）、任务清单是否覆盖全部设计模块、测试用例是否覆盖全部验收标准。覆盖之外还要查**断言强度**：每条用例答得出"实现错成什么样时它会失败"、性能类用例写明数据量级（见 04 模板自检），覆盖够但断言抓不住缺陷的全绿没有意义。发现缺口先补文档再编码，不带缺口开工。轻量级变更没有设计文档与任务清单，门禁只保留最后一条：spec.md 的每条验收标准都必须在冻结用例的覆盖矩阵中有对应用例（见 lite-spec 模板自检）。

## 阶段 3：编码（角色：开发）

1. 编码开始前先阅读 [references/coding-checklist.md](references/coding-checklist.md)，把它作为整个编码阶段的规范；每个模块完成后按清单自检，全部通过才能进入阶段 4。
2. 以 `docs/02-design.md` 为唯一依据、按 `docs/03-tasks.md` 顺序逐任务实现，每个模块附带单元测试——每个公共类/公共方法至少覆盖正常路径、边界条件、异常场景三类用例。**单元测试与冻结用例双向追溯**：测试方法名或 docstring 携带 `04-test-cases.md` 中对应的用例 ID（如 `TC-18`），对应不到需求级用例的纯内部细粒度用例可豁免——测试方法数与用例数不一致时，关系靠 ID 讲清楚，不靠事后散文解释。每完成一个任务：真实运行构建与测试，通过后按阶段 0 的授权约定完成 git 提交（未获授权时只暂存并给出提交信息）并在任务清单中勾选。
3. 客观裁判规则：**构建、Lint、单元测试必须真实运行命令并以命令退出结果为准**，不得以"应该没问题"代替。全绿才能进入阶段 4。
4. 编码过程中同步编写、编码完成后定稿 `docs/05-dev-doc.md`（模板见 [references/05-dev-doc-template.md](references/05-dev-doc-template.md)）：工程背景（新建还是改造既有工程）、与设计的差异及原因、实际目录结构、实现类图、接口实现清单、单元测试清单、本地运行指南。
5. 发现设计不合理时，先更新 `docs/02-design.md`（在文档中追加变更记录），再改代码——不允许代码与设计文档静默分叉。

## 阶段 4：测试（角色：测试）

1. 执行 `docs/04-test-cases.md` 中的全部用例，**以外部可观察行为为准真实调用**——Web 接口用真实 HTTP 请求（curl 等），CLI 程序用真实子进程调用（看 stdout/stderr 与退出码），库/模块用真实调用方代码；判断标准：不读内部实现也能完成的调用方式才是合格载体。有 UI 的项目按可行性降级——能起浏览器自动化就跑页面断言，起不了就以接口层用例覆盖 UI 背后的逻辑、UI 本身留待人工验收时检查。结果记录到 `docs/06-test-report.md`（模板见 [references/06-test-report-template.md](references/06-test-report-template.md)），报告需同时汇总单元测试结果（命令、通过率、覆盖率）。
2. **非功能需求验证**：SRS 中每条 NFR 都标注了验证方式，逐条执行可行的验证（性能用真实数据量的基准测试、安全按编码清单的安全项复查），结果写入测试报告；本环境确实无法验证的（如分布式压测），在报告中明确标注"未验证"及原因，不许默默跳过。
3. 有用例失败 → 生成缺陷报告（复现步骤、期望/实际、来源用例 ID）→ 回到阶段 3 修复 → 修复后**回归执行全部用例**（不只是失败的用例，防止修复引入新问题）→ 再出报告。**每轮修复必须附带根因与修复策略**（记入缺陷表的"根因/修复策略"列），禁止只针对症状打补丁——连续两轮根因相同或轮次趋势反复波动，说明修复在打地鼠，应提前停止循环向用户报告，而不是等满 5 轮；根因记录同时也是熔断时升级报告的现成素材。
4. **熔断规则**：缺陷修复循环最多 5 轮。超过 5 轮仍未全绿，停止循环，向用户报告：迭代历史、仍未通过的用例、你的根因分析、需要用户决策的问题（如需求本身是否可行、是否接受带缺陷交付）。**用户给出新指引后熔断计数清零，从该指引重新进入修复循环**——指引带来的新信息意味着之前的循环已失效。
5. **阻塞（BLOCKED）处理**：因环境前置不满足（缺运行时/依赖、外部服务或硬件不可用、需要真实账号授权）而**根本无法执行**的用例标记为 BLOCKED，与 FAIL 严格区分：BLOCKED 不是失败，不生成缺陷、不触发修复循环，也**不计入通过率**（通过率只算真实跑出了 PASS/FAIL 的用例）；但交付前不允许遗留未处理的 BLOCKED——要么补齐环境后补跑、改为真实的 PASS/FAIL，要么在验收汇总中显著列出（阻塞原因、解除条件、受影响需求），由用户决定搭环境还是接受该范围未验证。**严禁以静态阅读代码"推断应该通过"把 BLOCKED 记成 PASS**——没跑就是没跑。

## 变更处理（任何阶段都适用）

开发中途用户提出新需求或修改需求时，不允许直接改代码了事——变更沿文档链向后传播，保证产物与代码始终一致：

1. 新需求写入 `docs/01-srs.md` 的变更记录；SRS 已冻结的需求变更，需用户确认后再重新基线化
2. 评估影响范围，沿链更新：`docs/02-design.md`（受影响的模块、接口、表结构）→ `docs/03-tasks.md`（受影响的任务与新增任务）→ `docs/04-test-cases.md`（新增/修改用例，注明变更原因）
3. 沿链更新完成后，**对受影响范围重跑一次一致性检查**（新需求是否被设计覆盖、新验收标准是否有用例）——一致性检查不能只在首次编码前当门禁，变更后的链路可能带伤；查完无缺口再动代码
4. 然后进入编码与测试循环

反向同样成立：编码或测试中发现需求本身有误，先改 SRS 再沿链往下改，而不是只改代码。

**交付后的新需求**（借鉴 OpenSpec 的按变更组织）：作为一次独立的流水线运行，产物放在 `docs/changes/<变更名>/` 下、沿用同一套模板；完成后把需求增量合入主 `docs/01-srs.md`，变更目录保留归档——主文档始终保持"当前系统是什么样"，归档目录保留"每次是怎么变过来的"。

**全自动模式**：用户事先声明"跳过确认""全自动跑"等，仅跳过**检查点 1（SRS 确认）**；澄清提问照常进行（那是获取信息，不是审批）。**检查点 2（最终验收）永不跳过**——交付责任必须有人签收，全自动模式的产出一样要等用户验收。

## 最终验收

1. 验收前先做**收敛核对（借鉴 Spec Kit 的 converge）**：任务清单全部勾选、需求覆盖矩阵全部有测试用例、NFR 全部验证或标注未验证原因、无未处理的 BLOCKED 用例（已补跑出真实结果，或用户明确接受该范围未验证）、`docs/00-constitution.md` 的质量底线逐条满足。任何一项不满足，先补齐再交付。
2. 向用户汇总：交付物清单（代码位置、各阶段文档）、测试报告结论、遗留问题。
3. **👤 人工检查点**：请用户验收。验收不通过的意见视为新需求或新缺陷，从阶段 1（新需求）或阶段 4（新缺陷）重新进入流程。
4. 验收通过后，流程结束。**复盘（借鉴 BMAD 的 learn & adjust）**：把本次运行的经验教训追加到 `docs/lessons.md`（每次运行几行：哪个环节卡壳、模板哪里不顺、对照 `03-tasks.md` 预估工时记录估算偏差及偏差来源、下次怎么改）——阶段 0 会读取它，让流程在多次运行间自我改进。**教训升级机制**：复盘时若发现同类教训已在既往运行中出现过（第二次及以上），不允许只再记一遍——项目级的教训必须改写为 `docs/00-constitution.md` 的明确条目，流程级的教训（对自托管本仓库的用户）沉淀进 SKILL.md 规则；"被记住"不等于"被修正"，复述两次的问题就是流程自己的缺陷。**增长管理**：lessons.md 只追加会无限膨胀、拖累阶段 0 的读取——累积约 10 次运行后，复盘环节须做一次提炼：已升级为规则的条目压缩为一行索引（注明"已固化于 ××"），原始内容整体移入 `docs/lessons-archive.md` 归档。
