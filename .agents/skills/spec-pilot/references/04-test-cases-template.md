# 测试用例模板

> 使用说明：在写任何代码之前，仅依据 `docs/01-srs.md` 与 `docs/02-design.md` 填写本模板（轻量级变更依据 `docs/changes/<变更名>/spec.md`），生成后即冻结。禁止参考任何现有代码实现——用例验证的是"需求是否被正确实现"，而不是复述实现行为。接手已有代码的项目时，本模板由只拿到需求/设计文档的子代理填写（见 SKILL.md"冻结测试用例"）。

## 1. 用例清单

| 用例 ID | 来源需求/验收标准 | 前置条件 | 步骤 | 输入 | 预期结果 | 失效检测点（实现错成什么样时本用例会失败） |
|---------|-------------------|----------|------|------|----------|--------------------------------------------|
| TC-01 | FR-1 / AC-1 | | 1. … 2. … | | 可观察的输出/退出码/状态变化 | 如：返回字段缺失/顺序颠倒/退出码非 0 时失败 |
| TC-02 | FR-2 | | | | | |

要求：

- 用例 ID 全局唯一、连续编号（TC-01、TC-02……）；编码阶段单元测试的方法名或 docstring 须携带对应 ID，保证与本表双向追溯
- 预期结果必须是**外部可观察**的（输出内容、退出码、返回值、持久化后的状态），不允许"正常工作""提示错误"这类无法判定的表述
- 除正常路径外，必须覆盖边界值（空输入、空列表、0、最大值、超长字符串）、非法输入与失败场景（外部依赖不可用、资源不存在、并发冲突）
- 一条验收标准可拆成多条用例，但每条用例必须能追溯到至少一条需求或验收标准
- **每条用例必须填得出"失效检测点"**：反向自问"实现写成什么样（少个判断、边界取错、并发未加锁……）时这条用例会失败"。答不出具体错误形态的，是断言太弱的假用例（只覆盖"能跑"、覆盖不了"正确"），必须加强断言或拆细后重写
- **性能/容量/并发类用例必须写明数据量级与负载构造方式**（如"预置 10 万条记录""50 并发持续 30 秒"），禁止在空数据、单请求下验证性能类验收标准——那种全绿不证明任何东西

## 2. 需求覆盖矩阵

| 需求/验收标准编号 | 对应用例 ID | 覆盖情况 |
|-------------------|-------------|----------|
| FR-1 / AC-1 | TC-01, TC-02 | ✅ 已覆盖 |
| NFR-1 | TC-20 | ✅ 已覆盖 |
| FR-3 | — | ❌ 缺口 |

每条功能需求的每条验收标准、每条可验证的非功能需求都必须至少对应一条用例；出现"—/缺口"行必须先补用例，一致性检查不通过不得进入编码。

## 3. 非功能需求验证安排

| NFR 编号 | 验证方式 | 对应用例 ID / 手段 |
|----------|----------|--------------------|
| NFR-1 | 真实数据量基准测试 | TC-xx |
| NFR-2 | 按编码清单安全项复查 | 人工/脚本复查项 |

本环境确实无法验证的 NFR（如分布式压测）在此标注，阶段 4 测试报告中必须写明"未验证 + 原因"，不许默默跳过。

## 5. 产出物自检

> 通用规则"对照模板逐项自检"的落点；全部勾选后用例才视为冻结，可进入一致性检查与编码。

- [ ] 用例在编码前生成，来源仅为 SRS/设计（轻量级为 spec.md），未参考任何实现代码
- [ ] 每条用例有唯一 ID、明确的前置条件、步骤、输入与可观察的预期结果
- [ ] 覆盖矩阵无缺口：每条验收标准与可验证 NFR 至少对应一条用例
- [ ] 边界、异常、失败场景用例已覆盖，不只写正常路径
- [ ] 每条用例的"失效检测点"成立：能指出至少一种具体实现错误会使该用例失败；答不出的弱断言已重写
- [ ] 性能/容量/并发类用例写明了数据量级与负载构造方式，不在空数据或单请求下验证
- [ ] 全部用例可通过外部可观察行为执行（真实 HTTP 请求 / 子进程调用 / 真实调用方代码），不依赖读取内部实现
